## T173 — el CI en cada PR, no en cada push

**Estado:** hecho en lo que se puede medir aquí. **El workflow nuevo se mide en este mismo PR**:
en un `pull_request`, GitHub usa el `ci.yml` de la rama, así que la primera corrida de la PR es la
primera corrida del workflow optimizado. Lo que no se puede medir hasta que se fusione es el efecto
en la cola de `main` y en las reglas de protección.

**Commit:** `ci: medir en cada PR y no en cada push (T173)`.

**Qué cambia:**

1. **Fuera el `push` de ramas.** Antes `push: branches: ['**']` y `pull_request` disparaban los dos
   el CI: cada empujón a una rama con PR ejecutaba todo dos veces, con grupos de concurrencia
   distintos, así que ninguno cancelaba al otro. Ahora sólo `pull_request` y `merge_group`.
2. **`main` no corre aquí.** Lo que llega a `main` ya pasó el listón en su PR; de `main` se encargan
   `release-please.yml` y `release.yml`. La garantía pasa a branch protection (o merge queue).
3. **El filtro de rutas, en un trabajo y no en `on:`.** Un workflow que no se dispara por `paths`
   deja sus checks en «Pending» y bloquea el merge. El trabajo `cambios` publica `codigo`,
   `packaging`, `desktop` **y la lista de sistemas de cada matriz**; los demás se saltan con `if`,
   y un trabajo saltado por condición cuenta como «Success». La lista va aparte porque `matrix` no
   se puede usar en un `if` de job: el `if` mira sólo `needs` y la matriz se construye con
   `fromJSON`.
4. **`pruebas-windows` separado del empaquetado.** Las pruebas de Windows pasan de ~30 min (dentro
   del empaquetado, con Rust) a ~3 min en paralelo.
5. **E2E en dos mitades y `e2e-fallo` aparte.** `--shard=1/2` y `--shard=2/2`; el camino del
   proveedor caído deja de retrasar a las dos mitades.
6. **Empaquetado según lo que se tocó.** Linux siempre que cambie código (build de verificación y
   `smoke`); Windows sólo con cambios de empaquetado o del árbol de Rust; macOS fuera del PR (sus
   `.dmg` y la firma viven en `release.yml`). Se enciende con la variable `CI_MACOS_EN_PR=true`.
7. **Cachés.** `Swatinem/rust-cache` en vez de `actions/cache` sobre `target/`; caché de capas de
   Docker con `scope` propio; caché de Chromium para Playwright; `BUN_VERSION` en un solo sitio.
8. **`release.yml`.** Los mismos `scope` de caché de Docker y `Swatinem/rust-cache` en los
   instaladores. Se conserva el `publicar` por id de T172 y los SHA de las acciones que subió
   Dependabot.

**Verificación:**

- Los dos YAML parsean con `Bun.YAML.parse`; `ci.yml` declara `on: [pull_request, merge_group]` y
  los trabajos `cambios`, `calidad`, `pruebas-windows`, `docker`, `e2e`, `e2e-fallo`, `empaquetado`
  y `desktop`.
- **53 bloques `run` en bash** extraídos de los dos workflows y pasados por `bash -n`: 0 errores.
- **`actionlint 1.7.12`** sobre los dos workflows: **0 errores**. La primera versión de este
  `ci.yml` usaba `matrix.os` en el `if` de `empaquetado` y de `desktop`; GitHub la rechazaba con
  «workflow file issue» y el run no llegaba a tener jobs. La matriz ahora la decide `cambios` y se
  construye con `fromJSON`.
- `bun test scripts/desktop.test.ts scripts/package.test.ts` → **75 pasan, 0 fallan** (leen el YAML
  y exigen la cadena `servidor → anfitrión → único → instalador`).
- `bun run typecheck` → 0; `bun run lint` → 0 (27 warnings preexistentes).
- `bun test` → **3095 pasan, 10 fallan**, los 10 por `EPERM ... uv_spawn 'git'` del sandbox en
  `scripts/agente.test.ts` y el gancho; son los mismos de antes del cambio.
- **No medido aquí:** los minutos de runner y la cola de `main`. El PR es la primera corrida real
  del `ci.yml` nuevo; la primera semana de datos de Actions dirá si el ahorro estimado se cumple.

**Ajustes manuales que hay que hacer en GitHub** (si no, la PR puede quedar esperando checks que ya
no se publican):

- **Required checks:** sólo `cambios` y `calidad` corren siempre. Los demás son condicionales:
  `pruebas-windows`, `docker`, `e2e (1)`, `e2e (2)`, `e2e-fallo` y `empaquetado (ubuntu-latest)`
  cuando hay código; `empaquetado (windows-latest)` sólo si se toca el empaquetado; `desktop` sólo
  si se toca `desktop/`. **No pongas como required un check condicional**: si el job no se crea, el
  check no aparece y la PR se queda esperando. Requiere `cambios` y `calidad`, deja el resto como
  informativos, o enciende la merge queue.
- **Quita** `empaquetado (macos-latest)` y `desktop (macos-latest)`: ya no se publican en PR.
- **Opcional:** `CI_MACOS_EN_PR=true` devuelve macOS al trabajo `desktop` sin tocar el YAML.
- **Recomendado:** encender la merge queue y dejar que ella imponga el orden, en vez de «Require
  branches to be up to date».
