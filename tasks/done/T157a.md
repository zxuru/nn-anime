## T157a — La compilación cruzada del anfitrión (tarea insertada)

**Estado:** hecho en lo que se puede medir aquí. La compilación cruzada **no se ha ejecutado**: el
árbol de Rust no se compila en esta máquina (sin HTTPS, `cargo` no alcanza crates.io).

**Commit:** `fix(package): la compilación cruzada del anfitrión y la firma de los dos ejecutables (T157a)`.

**Por qué existe esta tarea:** T157 metió el anfitrión en el instalador y, para no publicar un binario
de la arquitectura equivocada, puso una comprobación que **paraba** cuando el objetivo no era la
máquina. Eso era correcto para no mentir y **rompía la release**: `macos-latest` es arm64 y de ahí
salen los dos `.dmg`, así que la vuelta de Intel habría fallado, y con `fail-fast: false` y el trabajo
`publicar` colgando de `instaladores`, no se habría publicado **nada**. La comprobación tapaba el
problema en vez de resolverlo.

**Qué entra:**
- `rustTriple(platform, arch)`: el triple de Rust de cada objetivo (`x86_64-apple-darwin`,
  `aarch64-pc-windows-msvc`…), con `platformName` para que `win32`/`windows` y `darwin`/`macos` no se
  confundan —confundirlos buscaría un `.exe` como si no lo fuera—.
- `hostBinary` busca en `target/<triple>/release`, que es donde escribe `cargo build --target`.
  Buscar en `target/release` encontraría el binario de la máquina.
- `buildDesktop({ target })` acepta una clave de `TARGETS`, pasa `--target` **siempre** —también en la
  compilación nativa, para que la ruta del binario sea una sola y no haya un caso probado y otro
  no— y añade el objetivo con `rustup target add` cuando la compilación es cruzada.
- `stageDesktop` busca el binario del **objetivo** y, si falta, nombra el comando exacto que lo
  compila (`bun run desktop:build --target=darwin-x64`).
- La release pide `desktop:build --target=${{ matrix.target }}`.
- **Los dos ejecutables de Windows se firman.** Es un defecto que introdujo T157: el acceso abre el
  anfitrión, así que firmar sólo el servidor dejaba el aviso de SmartScreen justo en el ejecutable que
  se lanza al pulsar el acceso. Ahora se firma también donde `cargo` lo deja, antes de que el paso del
  instalador lo copie al lado del servidor.

**Verificación en esta máquina:**
- `bun run typecheck` **exit 0** · `bun run lint` **exit 0**, con **las mismas 3 advertencias** de la
  línea base.
- `bun test scripts/desktop.test.ts scripts/package.test.ts` **42 pasan, 0 fallan** (eran 38).

**Mutación medida:** devolver `hostBinary` a `target/release` —el defecto que la tarea corrige— hace
fallar **exactamente 1** guarda: «el binario sale del directorio del triple, no de `target/release`».
Restaurado, 18/18.

**Un aviso propio, corregido:** la guarda de la release comparaba una cadena con una expresión de
Actions (`${{ matrix.target }}`) dentro, y eso metía una advertencia nueva de
`noTemplateCurlyInString`. Ahora se compara con una expresión regular, y el lint volvió a 3.

**Consecuencia:** el `.dmg` de Intel ya no depende de que un humano se acuerde de compilar cruzado:
sin `--target`, las dos vueltas de macOS compilarían el anfitrión de la máquina y el `.dmg` de Intel
llevaría el de Apple Silicon, y hay una guarda que lo impide.
