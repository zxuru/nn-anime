## T215 — `tauri-action` no veía el borrador de la release

**Estado:** hecho.

**Commit:** `fix(release): el borrador se resuelve por id para tauri-action (T215)`.

**El síntoma, con la release ya desbloqueada:** el run del tag `v0.8.0` (43341876306) pasó
`comprobar` y `docker`, y los instaladores de macOS y Linux quedaron verdes, pero el de Windows
falló en el paso de `tauri-action` con:

```
Looking for a draft release with tag v0.8.0...
"releaseName" not set but required to create release.
Couldn't find release with tag v0.8.0. Creating one.
##[error]Release not found or created.
```

El borrador existía (id 441048948) y el `gh api` del repositorio lo devolvía: el que no lo veía era
el listado de la acción. `releaseDraft: true` no admite encontrarlo publicado: con el listado vacío
intentaba crear otro release para el mismo tag y moría en `"releaseName" not set`, que el workflow
no pasa a propósito —la release entera la escribe `release-please`—.

**Por qué no era del bump de dependabot:** el pin anterior (`944946e3`) era la **etiqueta anotada**
`v1`, y su `object.sha` es el mismo commit que el pin nuevo (`1deb371b`, `action-v1.0.0`). Es el
mismo código: la `0.7.0` publicó con él («Found draft release with tag v0.7.0 on the release list»)
y la `0.8.0` no. Lo que cambió fue el listado, no la acción.

**El arreglo:** un paso nuevo en el trabajo `instaladores` resuelve el borrador **por id** con el
mismo `gh api` que usa `publicar` y se lo pasa a la acción como `releaseId`, que se salta la
búsqueda por tag. Va antes de compilar, así que si el borrador no aparece el run falla en segundos.
`docs/release.md` lo cuenta en «`tauri-action` y el borrador que no encuentra».

**Verificación:** `actionlint` sobre `release.yml` → 0. YAML parseado con `Bun.YAML.parse` → cuatro
trabajos y el paso en su sitio. La verificación de verdad es el run del tag: `comprobar` verde,
`instaladores` de las cuatro plataformas verdes, `publicar` publicando y la release con assets,
`latest.json` y `.sig`.

**Corrección (T216):** la causa no era «el listado no veía el borrador» a secas: el borrador
estaba **desvinculado** de su tag porque el tag se había movido, y GitHub lo renombró
`untagged-a92afb0a6a8114e6d1cb`. El listado de releases sí devuelve borradores; lo que no había
era una release con `tag_name == "v0.8.0"`. Se arregló re-enlazándolo con
`PATCH /releases/<id> -f tag_name=v0.8.0`. El paso `releaseId` se queda: resuelve el borrador por
id y falla en segundos si no está, que es justo lo que hizo falta ver. Lo contado está en
`docs/release.md` → «Mover el tag desvincula el borrador».
