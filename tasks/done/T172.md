## T172 — el circuito de la release y el listón de `main` con Biome 2.6

**Estado:** hecho en lo que se puede medir aquí. **Los dos workflows no se han ejecutado en
GitHub desde esta rama**: el primer release posterior al merge es el que los mide de verdad.

**Commits:**

- `fix(ci): el listón de main con Biome 2.6 (T172)` — `biome.json`.
- `fix(release): disparar y publicar la release por id (T172)` — `release-please.yml` y `release.yml`.

**Qué se arregla:**

1. **El lint de `main`.** El bump de Biome a 2.6.2 (PR #16) activó el formateo de Markdown y YAML
   y dejó 142 errores en los `.md` del repositorio y 3 en los YAML de `.github`. El listón de main
   estaba en rojo desde ese merge. `biome.json` sube el esquema a 2.6.2 y **excluye Markdown y
   YAML** del chequeo: es lo que hacía 2.5.15, y los documentos del repositorio están escritos a
   mano (las tablas se refluyen enteras si se dejan al formateador). No se toca ni un `.md` ni un
   `.yml` por formateo.
2. **El disparo de la release.** `release-please` crea el tag con el `GITHUB_TOKEN` y GitHub no
   inicia workflows por eventos de ese token. Ahora `release-please.yml` pide `actions: write` y,
   cuando `release_created == 'true'`, lanza `release.yml` con `workflow_dispatch` sobre el tag
   recién creado. Es el camino que se usó a mano para publicar la 0.3.1.
3. **La publicación.** `release.yml` resolvía el release por tag, y `GET /releases/tags/$TAG` no
   devuelve borradores: por eso creaba un segundo release con el mismo tag, subía los assets a uno
   y publicaba el otro. Pasó con la 0.3.0 y con la 0.3.1 (los 8 assets quedaron en un borrador y
   se publicó uno vacío). Ahora:
   - resuelve el borrador **por id** con `GET /releases?per_page=100` (que sí incluye borradores);
   - si ya hay una release publicada, falla y no la toca;
   - crea el borrador por la API para quedarse con su id en la misma respuesta;
   - borra los assets del intento anterior antes de subir (reintentos idempotentes);
   - sube cada archivo al `upload_url` de ese id, no al tag;
   - publica **ese id** con `PATCH draft=false make_latest=true`;
   - **verifica** que el número de assets es el de `release/` y que `draft` quedó en `false`; si no,
   el trabajo falla en vez de dar verde con una release vacía.

  lectura del código y por el `bash -n`; el primer release que pase por aquí es la medición que
  falta. Tampoco se ha medido el `gh workflow run` desde `release-please.yml`, por el mismo motivo.
