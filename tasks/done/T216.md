## T216 — la causa real del borrador perdido, y la 0.8.0 publicada

**Estado:** hecho.

**Commit:** `docs(release): mover el tag desvincula el borrador (T216)`.

**Qué pasó, en orden.** La `0.8.0` quedó en borrador porque `comprobar` falló: un test de la caché
de búsqueda hacía red real contra AniList y rozó el plazo de 5 s de `bun test` (T214). Con el test
arreglado y el tag re-apuntado al commit corregido, el run siguiente volvió a fallar, ahora en el
trabajo de Windows: `tauri-action` no encontraba el borrador y moría con `Release not found or
created.` (T215).

**La causa del segundo fallo no era la acción.** El pin anterior de `tauri-action` era la etiqueta
anotada `v1` y su `object.sha` es el mismo commit que el pin nuevo: mismo código con el que la
`0.7.0` publicó. Lo que cambió fue el tag: **mover el tag de un borrador lo desvincula**, y GitHub le
pone nombre de tag `untagged-<sha>`. Una sonda con el token del workflow lo enseñó:

```
441048948   untagged-a92afb0a6a8114e6d1cb   true
429459086   v0.7.0                          false
```

El listado de releases sí devuelve borradores; lo que no había era una release con `tag_name ==
"v0.8.0"`, que es lo que filtra la acción. Se arregló re-enlazando el borrador por id
(`PATCH /releases/441048948 -f tag_name=v0.8.0 -f target_commitish=e24ffeb`), re-lanzando los
trabajos que fallaron (`gh run rerun 43345282421 --failed`) y dejando el paso `releaseId` de T215,
que hace explícito el destino y falla en segundos si el borrador no aparece.
